# fn-grill：需求打磨（fn-ladder 第①阶段）

把模糊任务逼问清楚并落盘为**两份文档**（路径：执行工作目录下 `fn_docs/`——**固定目录与文件名，不建任务子目录**，一个工作目录同一时间只有一个活跃任务）：

- **`README.md`**——面向用户查阅：通俗的功能说明与使用流程，不含复杂术语；本阶段之后保持静态（只有需求变更时经本阶段更新）。
- **`requirements.md`**——面向后续任务划分：术语表、需求条目（含验收方式）、范围外、变更记录。

本阶段是这两份文档唯一的写入者。

## 进入检查

- `fn_docs/` 存在 = 此前已走过步骤：读文档判断停在哪一步，按用户当前需求继续（修改需求、或指路后续阶段），**不拦、不清理**；读到放弃记录 → 先问处置（续作还是遗留删除）。
- `fn_docs/` 不存在 = 全新任务，从需求打磨开始。
- **小任务豁免**：预判 ≤2 个函数、或纯配置/样式/文档类非函数工作 → 提示"不值得走全流程"，经用户确认后转常规流程，不建 `fn_docs/`。

## 提问机制

把需求建模为**决策树**，按**轮次**推进：**前沿** = 前提已落定、现在就能问的问题。每轮把整个前沿打包问完，每题编号、附你的推荐答案，等用户回答后重算前沿再问下一轮。答案依赖本轮未决问题的，留给后面的轮次。

- **事实归你，决策归用户。** 需要事实（代码现状、环境、工具）自己查或派子代理，绝不问用户能查到的东西。
- **模糊术语当场逼精确**："账户"指 Customer 还是 User？术语不精确，后面职责一句话就写不出来。
- **边界场景压测**：用具体极端场景（非法输入、部分失败、空数据、超大规模）逼出异常行为。
- **存量改造必与代码交叉验证**："你说支持部分取消，但现有代码只取消整个订单——哪个对？"
- **提问附通俗解释**：技术概念（如"错误处理风格"）必须先用平实语言解释选项含义再提问，不许甩术语。

## 必问清单（八条，一条不漏）

1. **环境与技术栈选型**：语言、框架、运行时、已有代码库约定、错误处理风格（异常/返回错误码）、日志方式（绝不遗漏、不许替用户默认）。
2. 根本目的：任务为什么存在，成功长什么样。
3. 每个功能口的输入/输出/错误的数据形状。
4. 边界与异常行为。
5. 非功能约束：性能、并发、平台、安全。
6. 外部依赖：库、服务、文件系统、网络。
7. **每条需求的验收方式**——它是后续核验命令的种子，此阶段不定，实现时必被现编放松。
8. 范围外清单：明确不做什么。

## 铁律

- 前沿清空才算谈完；**谈完 ≠ 可以做**。写出 README.md 与 requirements.md、向用户报告，**停在门口**，等用户显式同意才进 fn-divide。
- 禁止擅自推进；禁止把"细节实现时再定"当作答案——验收方式未定的需求就是假完成的种子。
- 最低必答集：环境选型、每条需求的验收方式、范围外——三条**不可跳过**；其余五条用户说"跳过"则按推荐答案落盘并标注"用户跳过，采用推荐"；禁止全部跳过。

## 红旗（出现即停）

| 念头 | 现实 |
|---|---|
| "问太多了，用户会烦" | 漏问的问题在实现期贵十倍 |
| "这个细节实现时再定" | 验收方式悬空 = 假完成种子 |
| "环境就用项目里现成的" | 环境选型必须显式确认，不许默认 |
| "文档回头补" | 谈完当场写盘，对话记忆不可靠 |

## README.md 模板（用户向，零术语，尽可能详细）

任务名由 fn-grill 从根本目的提炼，随文档在门口确认。

```markdown
# <任务名>

## 工作流程
（程序的执行流程，尽可能详细、包含细节：按实际顺序，从程序启动到
结束经过哪些环节、每一步发生什么、条件分叉走向哪里）

## 项目功能
（另起一段，详细说明项目具备的功能：每个功能是什么、具体表现如何）
```

避术语铁律：出现的概念必须当场用平实语言解释清楚，不许甩专业词。（fn-merge 汇总版另有附文规则，见 fn-merge。）

## 出口

产物（README.md + requirements.md）呈现后**停**，显式提示两项：**下一步命令 `/fn-divide`**，或**修订本步骤**（指出产物哪里要改）；用户未显式选择前不推进。豁免场景出口：经确认后退出 fn-ladder，以常规流程实现。中途接手本阶段时，先按 FN-LADDER.md 中途进入协议对账。
