# fn-divide：函数划分（fn-ladder 第②阶段）

把需求文档划分为**分层责任文档**。**本阶段唯一产出物是 `responsibility.md`**，本阶段是它唯一的写入者；fn-implement 只读它。

## 进入检查

`fn_docs/requirements.md` 必须存在且经用户确认。没有 → 停，指回 fn-grill。中途接手先按 FN-LADDER.md 中途进入协议对账。**功能演进模式**（fn_docs 有 acceptance.md）：在既有责任文档上**只增不改旧块**——矩阵加行、函数树加新功能块；已 wired 的旧函数不动（结构性调整需经快速通道并留变更说明）。

## 划法

1. **需求条目 → 顶层函数**：一个功能口一个顶层函数，必须回链它负责的需求条目（R 编号）。
2. **顶层 → 二级 → …**：每层函数实现其上层函数内部需要的功能，层层下探。
3. **叶子为止**：实现单元的职责是**单一功能转变**即叶子；职责详述中出现两件不相干的事 = 该再拆。
4. **存量改造**：先探查现有代码，把任务映射为"改哪些现有函数 / 新增哪些函数"，进同一棵树；改现有函数按现状描述职责。

## 责任文档格式（概览树 + 矩阵 + 功能块递归分块）

```markdown
# 责任文档：<任务名>
> 由 fn-divide 产出与独占更新；fn-implement 只读。进度与状态见 implementation.md。
> 职责字段是**重写规约**：凭职责详述 + 签名意图（输入/输出），必须能完美复现该函数功能。

## 结构概览（纯结构，不带职责）
- parse_and_load ← R1
  - validate_header
    - check_encoding
  - transform_rows
- export_report ← R2

## 需求覆盖矩阵（P1 在 R 号后标注；非功能约束不进矩阵，fn-close 终检对照 requirements 非功能节）
| 需求 | 顶层函数 |
|---|---|
| R1 | parse_and_load |
| R2 [P1] | export_report |

## 共享函数（shared/：多顶层共用；矩阵挂全部受益需求）
- **<函数名>**（调用方：parse_and_load, export_report）
  - 职责：（详细说明）
  - 签名意图：输入: … / 输出: … / 错误: …
  - tested 策略：自有单测 | 上游覆盖: <函数名>
  - 核验命令：测试: <测试名/文件> | 上游覆盖: <函数名>

## 功能块 parse_and_load ← R1
（块引言：本功能口的需求、功能与职责——详细叙述，包括各种要求）

- **parse_and_load** [L0|新增]
  - 职责：（必须详细说明——重写规约）
  - 签名意图：输入: … / 输出: … / 错误: …（意图级三要素，精确签名真值在代码）
  - 调用方：程序入口
  - tested 策略：自有单测
  - 核验命令：测试: <测试名/文件>（只能继承 R1 的验收方式，不许现编放松）
  - **validate_header** [L1|新增]
    - 职责：（详细说明）
    - 签名意图：输入: … / 输出: … / 错误: …
    - 调用方：parse_and_load
    - tested 策略：上游覆盖: parse_and_load
    - 核验命令：上游覆盖: parse_and_load
    - **check_encoding** [L2|新增]
      - （同构递归，调用方：validate_header）
```

规则要点：

- **函数名与代码一致**（目标语言惯例），本阶段定名、门口确认，**全库唯一**；描述字段中文。
- 每函数块固定五字段：职责（详述）/ 签名意图（三要素）/ 调用方 / tested 策略 / 核验命令（前缀格式 `测试:` / `上游覆盖:`）。
- **子函数块嵌在父块内递归分块**（列表嵌套，不受标题层级限制）；顶层函数各成一个功能块大节，块引言详述该功能口的需求、功能与职责。
- `[新增]` / `[改造]` 标记：改造现有函数标 `[改造]`，职责写改造后的目标态。
- 不记文件路径（代码是真值）；**无状态列**——状态属于 implementation.md（fn-implement 的领地）。

## 产出前自检（双向拦截假完成）

- 矩阵正向：每条需求至少一个顶层函数负责——**无函数负责的需求 = 漏实现**。
- 矩阵反向 + 树：每个函数有调用链连到某个顶层入口——**连不到顶 = 死代码**。
- 每函数职责为单一功能转变；详述中出现多个不相干转变 = 再拆。
- 函数总数 > 20，或划分中函数数暴涨 → 预警拆解失控，向用户呈现并建议收缩范围。

## 铁律

- 呈现树 + 矩阵 + 自检结果后**停在门口**，等用户显式同意才进 fn-scaffold。
- 核验命令只能继承自需求验收方式；责任文档是静态契约，实现期只有本技能（含快速确认通道）能改它。
- 后续实现期发现结构性变化（函数增/删/拆/并/职责或调用关系变化）时，必须回到本阶段改本文档——这条写在文档头部，提醒所有后续读者。

## 出口

树 + 矩阵 + 自检结果呈现后**停**，显式提示两项：**下一步命令 `/fn-scaffold`**，或**修订本步骤**；用户未显式选择前不推进。
