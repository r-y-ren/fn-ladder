# fn-analyze：结果分析与改进提案（fn-ladder 数据驱动改进入口）

把运行结果数据与代码实现放在一起分析，产出**到函数级**的改进提案。三棒的专用合体：review 的结果轴扩展 + brainstorm 的方向发散 + grill 的定形出口。**分析、不实施**——同 on-ramp 哲学，出口交回单个技能。

它管的是验收的另一半：功能对不对归五阶段，**效果好不好归这里**——改了、验收通过了、分数没涨的"合法假完成"由效果闭环拦截。

## 进入检查

- `fn_docs/` 与代码在（无 → 指回 `/fn-grill` 或 `/fn-refactor`）。
- requirements.md 外部依赖节有**结果数据源**条目（拉取命令、格式与存放）。没有 → 停，先经 `/fn-grill`（演进模式）补定义。

## 机制

1. **拉数据（派子代理，隔离大输出）**：子代理按数据源条目拉取 → 快照存 `fn_docs/results/<日期>-<说明>.<ext>` 随 git 留痕 → 统计摘要（趋势 / 分布 / 异常 / 与上一快照对比）回主会话。拉取命令必须可复跑。
2. **三轴分析（主会话）**：
   - **结果轴**：统计摘要找现象——胜率变化、分布偏移、断崖、方差、同上快照对比；
   - **代码机械轴**：插件根 `scripts/fn-check.sh` 与 `scripts/fn-doc-lint.py`（先排除"数据差是因为代码坏了"）；
   - **职责关联轴（核心）**：现象 → 责任文档职责 → 函数——沿"哪个函数的职责覆盖这个行为"定位嫌疑人，不许跳过职责链直接猜。
3. **改进提案**（发散纪律同 fn-brainstorm：≥3 个方向、必含一个激进项），每条五字段：

   ```
   ### P1 <一句话方向> [优先级]
   - 现象：数据证据（快照对比的具体数字）
   - 假设：定位到函数——引责任文档职责（"X 的职责是…，而数据显示…"）
   - 改进方向：做什么（不写实现细节）
   - 预期信号：改完后结果数据应出现什么变化 ← 数据版验收方式的种子
   - 分流：参数/逻辑级（[改造] 现有函数）vs 结构性（回 fn-divide）
   ```

4. **效果闭环打分（铁律）**：对历史全部提案的预期信号逐条打分——**达成 / 未达成 / 反向**；未达成或反向 → 建议转 `/fn-brainstorm`（方案失效换思路）。
5. **报告落盘** `fn_docs/analyses/<序号>-<日期>.md`（本技能独占写——横向技能中唯一写盘者，理由：改进效果闭环需要历史对比）；必含"上次快照 vs 本次"对比节。

## 出口

提案逐条呈用户裁决（只报事实与建议，判定归用户）→ 选定项交 `/fn-grill`（演进模式开 R 条目，验收方式从"预期信号"命令化或写成可观察判据）→ 之后标准演进链。本技能不实施任何改动。

## 红旗（出现即停）

| 念头 | 现实 |
|---|---|
| "分数降了，直接改代码吧" | 只分析不实施——提案过 grill 才能动代码 |
| "现象很明显，不用引数字了" | 现象必须有快照对比的具体数字，防印象流分析 |
| "这个函数看起来可疑" | 定位必须经责任文档职责链，不许跳过关联直接猜 |
| "上次提案就不打分了" | 效果闭环是铁律——不打分的改进循环是盲飞 |
