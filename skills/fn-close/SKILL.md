# fn-close：收尾核验（fn-ladder 第⑤阶段）

对整个任务做终检并产出验收报告与**使用手册**。本阶段只读全部文档与代码、只写 acceptance.md 与 user-guide.md，**不改任何前序产物**（走查修复环的显式子代理除外，见下）。

## 进入检查

`implementation/functions.md` 函数大表全员 wired（用户明确要求提前验收时也可进入，报告中注明未完成项）。中途接手先按 FN-LADDER.md 中途进入协议对账。**功能演进模式**：终检为**全量**（新旧函数与需求一起过六道）；写新报告前，先把现版 acceptance.md 归档为 `acceptance-c<N>.md`（周期序号 c1、c2…）。此归档是验收报告唯一的周期性挪动，不与"fn_docs 原地保留"冲突——其余文档与旧归档一律不动。

## 六道终检（全过才算完成；交付型任务含可选第七道）

**六道是强制序列：逐道独立执行、逐道原样贴输出**（第七道仅交付型）。禁止跳道、合并、"其余同上"、只挑可疑的道跑——每道在验收报告对应节留原样输出，无输出 = 该道未过。修复后**六道全部重跑**（不是只重跑没过的那道）、重写报告。

1. **无残留桩 + 全量测试 + tests 镜像**：运行插件根 `scripts/fn-check.sh`（本技能目录上两级），贴脚本输出，三项全过才算过。
2. **接线实据**：逐函数静态调用点存在；顶层入口函数有实跑记录与可观察输出。
3. **矩阵双向复查**（对照 responsibility.md 需求覆盖矩阵）：先运行插件根 `scripts/fn-doc-lint.py`（状态词/批次一致/矩阵双向/函数唯一/死代码/档案-代码桩标记交叉/tracker 一致性 的机械校验），再人工复核——每条需求有函数负责且已 wired——**漏实现拦截**；每个函数有调用链连到顶层入口——**死代码拦截**；functions.md 状态与代码桩标记一致——**静默漂移拦截**；**tracker 核对**——每个 wired 函数五步行齐（七步的前五步；blocked/豁免有注记）、tracker 与 functions.md、git log 三方一致、豁免行无越权（active/consumed 对得上门的处置）。
4. **非功能约束对照**（对照 requirements.md 非功能节）：逐条验证约束与判据。
5. **报告完整性**：脚本输出已原样贴入、无"验收通过"式自封结论、末行固定句在。
6. **目录清点**（v1.5 目录契约）：`.scratch/` 逐目录二选一已执行（升格 → vendor/ 或 results/ **全量搬入不瘦身** / 删除仅限确认无价值的纯缓存）——无主暂存文件 = 不过；`fn_docs/vendor/` 逐件核 provenance 六字段（来源/抓取日期/版本/许可/用途/血统链）+ SHA256SUMS 可复验；外部数据源登记（requirements 外部依赖节）完备性一并核；**参考资料登记完备性同款核**（requirements 参考资料节与实际文件对得上、过期有"历史参考"标注）；**环境可复建**——依赖清单齐（requirements/lock 等已入库）、`fn_work/.venv`（或等价）在位或可由清单复建。

（**交付型任务可选第七道：外发终检**——外发物三验：精确路径 + payload sha 对照 + 包体成员清单打印，三验全过才许外发；错发/同名件混淆 = 不过。）
（merge 任务另有专项：**源函数去向表**——inventory.md 每个函数必须有下落：保留 / 重命名→新名 / 合并→目标 / 删除→**理由必填**；无下落或删除无理由 = 终检不过。）

## 用户走查环（六道全过 → 手册成稿后启动；清零才许出门）

模拟真实用户走一遍手册，发现问题、修复、再走，循环至清零：

1. **走查**（派走查子代理——**派发词 = 下方《用户走查派发模板》原文照抄、只填【】槽位**）：产出**对抗发现表**（假设 | 证据 | 判定），分级 Critical（阻断）/ Important（误导与逻辑）/ Minor（体验）。
2. **修复**：实现类问题**显式派子代理执行 `/fn-implement`**（修复时同样遵循该技能文档更新的要求：四文档/tracker/核验/读回），子代理修复完毕后返回主对话继续循环；文档类问题指回 owning 阶段（手册自身错漏由本阶段直接改，改后读回）。
3. **复走查**：只核本轮修复面（scoped）→ 回第 1 步。**单环 5 轮封顶**，超限停下报用户裁决。
4. **清零出门**：Critical/Important 清零（Minor 留档注明）→ 因修复动过代码，**六道全部重跑、重写 acceptance.md**（同周期重写：旧版作废、git 留痕——与"修复后六道重跑"规则一致；跨周期旧报告才归档 acceptance-c\<N\>.md）→ 出报告。

## 审查对象

## 功能抬杠（题源 =【功能要求出处：默认 user-guide 承诺的功能目标】；假设由你自立，派发方不得供给）

## 覆盖骨架（四正交方向，每方向 ≥2 条自拟独立假设——与功能抬杠配额并行）
(a) 手册承诺一致性（照做能否到达承诺的功能目标）；(b) 测试有效性（假绿探测）；
(c) 手册/档案/代码三方一致性；(d) 运行时真值（真跑看行为，不只看断言）。
假设数量不设上限；你的声誉来自抓到别人没抓到的问题，而不是复述宣称——
但不成立的假设必须贴否证输出，禁止为凑数虚构发现。

## 验收报告（fn_docs/acceptance.md，本阶段独占写入；同时在对话中呈现）

```markdown
# 验收报告：<任务名>
> fn-close 独占产出。核验输出原样粘贴，禁止转述、禁止"概括为通过"。
> 本报告不宣布"验收通过"——终审归用户。

## 终检一览
| 终检 | 命令 | 结果 | 证据 |
|---|---|---|---|
| ① 桩+全量测试+镜像 | scripts/fn-check.sh | 三项全过 | §1/§2 |
| ② 接线与实跑 | — | 过 | §3 |
| ③ 矩阵双向 | scripts/fn-doc-lint.py | 0 错误 | §4 |
| ④ 非功能对照 | — | 逐条过 | §5 |
| ⑤ 报告完整性 | — | 无自封结论、末行固定句在 | — |
| ⑥ 目录清点 | — | scratch 清空/vendor 户口齐/数据源登记齐 | §6 |
| ⑦ 外发终检（交付型可选） | — | 三验过 | §7 |

## 1 桩检查（全量输出原文）
## 2 全量测试（全量输出原文）
## 3 接线与实跑（逐顶层函数：调用点检查 + 实跑输出原文）
## 4 需求→函数对照表（R → 函数 → 核验命令 → 结果行）
## 5 非功能约束逐条（约束 → 判据 → 验证输出）
## 6 目录清点（scratch 逐目录去向 | vendor 逐件六字段+SHA | 数据源登记核对）
## 7 外发终检（仅交付型任务：外发物 | 精确路径 | sha 对照 | 成员清单）
## 未完成项（仅提前验收时：函数 | 当前状态 | 原因）
## 源函数去向表（仅 merge 任务：源函数 | 去向 | 说明/理由）
```

- **粘贴分级**：全局性命令（①②③的实跑）贴全量原文；函数级证据在 §4 记命令+结果行——全量测试输出已天然覆盖每个函数的测试结果；§6/§7 输出体量小、恰是审计要害，一律全量原文。原样粘贴铁律约束的是**贴进来的部分不许转述**。
- 一览表只报事实（零命中 / 全绿 / N 项过），**任何位置不出现"验收通过 ✓"式自封结论**；报告末行固定一句：**"以上为终检事实，验收与否由用户判定。"**
- 任何一道终检不过：如实报告未过项与缺口，指回对应阶段（实现→fn-implement、划分→fn-divide、需求理解→fn-grill），**不许宣布完成**；修复后重跑**全部**终检、**重写** acceptance.md（旧版作废，git 历史留痕）——验收是全量快照，不是流水账。

## 收尾

**交付报告前自检（逐条对照，缺一不许交付）**：六道每道都有原样输出？user-guide 四节齐、走查环清零（或超限已报用户）？第⑤道报告完整性自查过了（无自封结论、末行固定句在）？未过项如实列出并指回对应阶段？——任一缺 = 回去补做。

- 验收后 `fn_docs/`（含 acceptance.md）**原地保留**供查阅、随 git 留痕；不移动、不归档、不清理。
- `fn_docs/` 此后存在即表示任务已有进度：后续会话按中途进入协议续走。
- **终审出口**：报告呈现后验收与否由用户判定；任务闭环时显式提示后续入口——新任务 → 新工作目录（或处置 fn_docs 后）`/fn-grill`；存量项目 → `/fn-refactor`；多项目合并 → `/fn-merge`。
- **终审停**：报告呈给用户，由用户判定验收——完成与否是用户的结论，不是本阶段的自我声明。
